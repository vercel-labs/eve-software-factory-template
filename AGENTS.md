# AGENTS.md

Guidance for AI coding agents working in this repository.

## Project overview

The eve Software Factory template: Foreman, an orchestrator agent built on the [eve](https://eve.dev) framework that turns work items into reviewed draft pull requests on the configured repository (`FACTORY_REPO`). Work arrives from GitHub (an issue labeled `factory` runs unattended; @Foreman mentions from owners/members/collaborators run attended), from Linear Agent Sessions, and from the HTTP intake API (`POST /intake/v1/tickets`, unattended). The orchestrator triages every item first with `triage_work_item`: one decision-model call that classifies the item, picks labels from the repository's existing vocabulary, checks it against likely duplicates, and returns a lane (`pipeline`, `clarify`, `answer`, or `duplicate`). On the `pipeline` lane it runs the stations in order: optional **researcher** (web research, when triage sets `needs_research`) → **analyst** (plan + acceptance criteria, own repo checkout) → **implementer** (codes, verifies, pushes a feature branch from its own checkout) → **reviewer** (independent verdict on the pushed branch, different model vendor, max 2 revision cycles). The **classifier** station is the fallback: it writes the clarifying questions on the `clarify` lane and stands in when triage itself fails. The orchestrator then opens a draft PR with `gh pr create --draft`; marking it ready parks on human approval, closing or reopening issues runs as reversible triage, and merging is not in the `gh` allowlist. GitHub access is the real `git` and `gh`, through `bash`. The orchestrator has no shell, on any run: its `bash` accepts only whole `gh` commands, which the app runtime parses against an allowlist, holds to the caller's trust class, and runs itself under a per-command credential lease. The stations run `git` and `gh` in their own shell in a sandbox, where a shell command gets a read-only credential at most; the implementer's `git push`, as a whole command, is run by the runtime under a lease of its own. Memory is eve's built-in file memory: a per-user `preferences` slot and a shared, per-repo `brain` slot (the **factory brain**: durable notes about the target repository), recalled before every turn. The brain is written only through the orchestrator (directly by trusted callers, behind approval for others, never by an unattended run) and is mounted read-only in the analyst, implementer, and reviewer. **Handoff artifacts** stay in **Vercel Blob**: long Markdown documents (research memos, analysis detail) that stations pass to each other by id under the reserved `artifacts/` prefix instead of inlining them through the orchestrator. The pipeline lives in `agent/instructions.ts`.

The whole agent is defined under `agent/`. eve discovers capabilities from the filesystem. See [`ARCHITECTURE.md`](./.github/ARCHITECTURE.md) for the component map, data flow, trust model, and boundaries.

## Setup & commands

```bash
pnpm install        # install dependencies (Node 24.x)
pnpm dev            # eve dev: local TUI; /login links a model provider, /model switches models
pnpm typecheck      # tsc (no emit) over agent/, evals/, tests/, and scripts/
pnpm check          # ultracite (Biome) lint + format check
pnpm fix            # ultracite (Biome) auto-fix
pnpm test           # vitest run: the deterministic, offline suite under tests/
pnpm test:watch     # vitest in watch mode
pnpm run discovery  # scripts/check-discovery.ts: fails unless eve discovery is ready with 0 errors / 0 warnings
pnpm build          # eve build
pnpm eval           # eve eval: run the evals suite (see tags below; costs real tokens)
eve deploy          # deploy to Vercel production (use this, not raw `vercel deploy`)
npx eve info        # print the discovered surface + discovery diagnostics (exit code is always 0)
pnpm validate       # check + typecheck + test + discovery in one command
```

**Verify changes with `pnpm validate` (lint, typecheck, the test suite, and discovery must all pass), then exercise the agent in the `pnpm dev` TUI.** `eve info` exits 0 even when the agent fails to compile, so its exit code gates nothing: `pnpm run discovery` runs `eve info --json` (engine in `scripts/discovery.ts`) and fails unless the report says `ready` with 0 errors and 0 warnings; it fills unset required env vars with inert placeholders, so it works on a fresh clone. The evals suite (`pnpm eval --tag fast`) guards routing and safety behavior against a real model; `pnpm eval pipeline/full-pipeline` runs the whole line and pushes a real branch, so run it deliberately and against a scratch repo.

## eve conventions

- **Read the relevant guide in `node_modules/eve/docs/` before writing code.** Don't invent framework APIs; confirm them against the docs (memory: `memory/file.md`; `decide`: `guides/decide.md`; custom channels: `channels/custom.mdx`).
- **Identity comes from the filesystem, never a `name` field.** A tool at `agent/tools/triage_work_item.ts` is the tool `triage_work_item`; a connection at `agent/connections/linear.ts` registers as `linear`; a memory slot at `agent/memory/brain.ts` is the slot `brain`; a subagent directory `agent/subagents/classifier/` is the station `classifier`.
- Authored slots: `agent/agent.ts` (model, compaction, session budget), `agent/instructions.ts` (`defineInstructions({ content })`, the orchestrator prompt; resolved at build time, injecting `FACTORY_REPO`), `agent/tools/*.ts` (`defineTool` / `defineWorkflowTool` / `disableTool`), `agent/memory/*.ts` (`defineMemory`), `agent/connections/*.ts`, `agent/channels/*.ts`, `agent/skills/<name>/SKILL.md`, `agent/subagents/<id>/agent.ts` (`defineAgent`), per-agent `sandbox.ts`, `agent/instrumentation/otel.ts` (`otel`, the process-wide trace policy). Shared code lives in `agent/lib/`, which eve does not treat as a slot.
- **Model assignments are centralized** in `agent/lib/models.ts` (the `MODELS` map). Every `agent.ts` reads its entry from there (`model: MODELS.<agent>`) instead of hardcoding a gateway id, so a model swap is a one-line edit in that file. `MODELS.decision` is not an agent: it is the decision model behind `decide()`. One split is deliberate: `implementer` runs the strongest coding model on a different vendor than `reviewer`, so the review stays independent; keep those two on different vendors.
- **Session budget:** `limits.sessionUsage` in `agent/agent.ts` is a runaway guard (100,000 output tokens per session window, plus eve's default 40M uncached-input cap restated because authoring the callback replaces it). Crossing it asks on the session's channel whether to continue instead of hard-stopping; a session with nobody to ask fails its next model call. Each station counts its own usage.
- **Channels:** `github` (eve GitHub channel via Vercel Connect, botName resolved from the connector's app slug; the dispatch hooks live in `agent/lib/github/hooks.ts` so they can be unit-tested and `agent/channels/github.ts` only wires them: `onComment` keeps the built-in mention/ignore rules, dispatches only for OWNER/MEMBER/COLLABORATOR commenters, and stamps `attributes.trusted`; `onIssue` dispatches only on the `labeled` action for the `factory` label, verifies the labeler holds at least triage permission (labels attached at issue creation also fire `labeled`), and rewrites the principal to the autonomous one, so the run is unattended by construction; `onCheckSuite` dispatches only for failed suites on `factory/*` pull requests, unattended, with the fix loop capped by counting attempt comments on the PR thread; `onPullRequest` dispatches a summary run on opened PRs, bot senders skipped, stamped summary-only with `stampSummary` so it can read and comment on that one pull request and nothing else; the channel file also replaces the `turn.started` handler with the factory's own per-turn checkout, `checkoutForTurn` in `agent/lib/github/checkout.ts`, which must never be handed back to the channel's default), `linear` (Agent Sessions; every session stamped trusted since workspace membership is the gate), `intake` (the HTTP intake API, below), plus the `eve` route-auth channel, whose dev-only `localDevUser` shim upgrades the local principal to a user and sets `allowAgentInfo` / `allowToolStubs` so local `eve eval` can read `/eve/v1/info` and stub tools.
- **Intake channel:** `agent/channels/intake.ts` is a custom channel (`defineChannel`) with its contract and pure helpers in `agent/lib/intake/ticket.ts` and the callback builders in `agent/lib/intake/callbacks.ts`. `POST /intake/v1/tickets` validates a strict `ticketSchema` (unknown fields are a 400, every field except `body` is a single line, the request is capped at 64 KiB) and starts an unattended session; `GET /intake/v1/tickets/:ticketId` reports status and the final message. Auth walks `vercelOidc()`, then the shared secret `FACTORY_INTAKE_TOKEN` (constant-time compare, at least 32 characters, a wrong bearer is rejected outright), then `localDev()`. The session's principal comes from `autonomousForTicket` and nothing in the request body reaches it. Submissions are idempotent on `externalId`: the ticket id is a digest of the verified caller and that id, and the session's address is `ticket:<digest of caller>:<ticketId>` (`ticketAddress`), so a ticket is bound to the caller that submitted it and a GET from any other caller is the same 404 as an unknown id. A ticket is one run: when it ends by asking for clarification, the answer comes as a new ticket with a new `externalId`, because resubmitting the same one is a no-op. Optional callbacks go only to hosts in `FACTORY_INTAKE_CALLBACK_HOSTS` (`host` or `host:port`, exact match) and only when `FACTORY_INTAKE_CALLBACK_SECRET` is set (a `callbackUrl` without the secret is a 400 `callback_not_configured`); they are signed in `x-factory-signature`, carry `sentAt` inside the signed body, and send an `idempotency-key` header. Errors returned to callers, on GET and in callbacks, are `{ code, id }` only (`publicError`), never the runtime's message. Custom routes must stay outside `/eve/v1/*`, which eve reserves.
- **Triage is a decision model, not an agent turn.** `agent/lib/triage/decisions.ts` holds the question sets and thresholds: `triageWorkItem()` asks one `decide` call (eve's `decide` from `eve/ai`, model `MODELS.decision`) for type, priority, complexity, actionable, needs_clarification, needs_research, a yes/no per existing repo label, and a yes/no per duplicate candidate, then derives the lane with `laneFor`; `diagnoseCiFailure()` sorts a failed CI log into code / flaky / infrastructure / configuration. Duplicate candidates' titles are passed in the decision state (`existing_issues`), not in question text: anyone can file an issue, and question instructions are where the model takes direction from. Label names stay in the question text, since only people with triage rights write them. `agent/lib/triage/ci.ts` holds `diagnosePullRequestChecks`, which reads a pull request's checks and returns a `status` (`passing`, `pending`, `cancelled`, `no-checks`, `failing`, or `failing-no-log`) with `fix_with_code`: true or false when a failed log was read and judged, false when nothing is failing, and null on `failing-no-log`, where the logs could not be read and the cause is unknown (never "the code is fine"). `agent/lib/triage/github.ts` holds the `gh` reads and writes around them (`fetchIssue`, `fetchLabels`, `findDuplicateCandidates`, `applyLabels`, `fetchChecks`, `fetchFailedLogs`), each taking a `GhRunner`. The root tools `triage_work_item` and `diagnose_ci_failure` wire the two together. Triage never offers the decision model a label that records a decision (`duplicate`, `invalid`, `wontfix`: `VERDICT_LABELS` in `agent/lib/triage/run.ts`), the factory label itself, or a label whose name contains a comma (`gh` splits `--add-label` on commas); those are a reader's call, and triage reports duplicate candidates separately. It returns `labels_not_considered`, the number of repository labels the model was not asked about (skipped by name, or beyond the limit of 40). Every function takes `decide` or the runner as a dependency so the test suite can drive it with a mock; keep it that way. A decision model can only pick among the options it is given, so labels are never invented and injected text has no free-form output to steer; question keys are positional so repository text can't shadow a core question.
- **Triage runs before the first turn when the work item is already known.** On a labeled issue (`stampIssueIntake` in `trust.ts`, set only by `onIssue`) and on an intake ticket, `agent/instructions/pretriage.ts` runs the same triage as the tool (`runTriage` in `agent/lib/triage/run.ts`, which `triage_work_item` also calls) before the orchestrator's first model call and hands it the result as a user instruction, so that call is not spent on asking for triage. It is a dynamic instruction with the work in a memo keyed on the turn: once per turn, afresh on a later turn, and a failure is kept as null so the orchestrator falls back to calling `triage_work_item` itself. Every other run (a mention, a CI fix, a summary, Linear, the dev TUI) returns before a sandbox is asked for. Three rules: eligibility comes from dispatch stamps only (`pretriageTarget`), never from the message; labels are applied only where `labelDecision` lets the caller apply them unasked, since no tool approval sits in front of this path; and the instruction carries closed-list values, label names, and issue numbers only, never an issue's or a duplicate's title, because an instruction is read with more weight than a tool result.
- **Subagents are the stations.** Five are declared under `agent/subagents/<id>/` (`classifier`, `researcher`, `analyst`, `implementer`, `reviewer`); `description` is required (the routing hint) and each station sets `tool: false`, since `defineAgent` carries no `outputSchema`. A `defineWorkflowTool` at `agent/tools/run_<id>.ts` is what the orchestrator actually calls: it blocks on `ctx.agent(id).send(message, { outputSchema, signal }).result()`, attaching the schema from `agent/lib/stations/schemas.ts` per call. Each wrapper's `approval` is `stationPolicy`, which denies a summary-only run and lets every other caller through. `result()` does not throw on failure, so every wrapper passes it through `stationOutput()` in `agent/lib/stations/result.ts`, which throws for failed, cancelled, or empty results; the orchestrator's retry-once rule keys on that tool error. The wrapper can't share the station's own name (`run_classifier`, not `classifier`): eve's compiler rejects a tool and a local subagent with the same public identity, `tool: false` notwithstanding. A declared subagent runs in a fresh child session and **inherits nothing** from the root (no instructions, skills, connections, tools, memory, or sandbox), so the orchestrator packs everything into the `message`, and any capability a station needs lives in the station's own directory (its `sandbox.ts`, its `tools/`, its `memory/`). Long documents travel between stations as **handoff artifacts**: the researcher and analyst save them with `save_artifact`, downstream stations open them with `read_artifact`, and the orchestrator relays only the id (the factories live in `agent/lib/artifacts/`).
- **Memory slots** are eve file memory (`fileMemory()` from `eve/memory/file`), one file per slot under `agent/memory/`: `preferences.ts` (scope `userScope` from `agent/lib/memory/scope.ts`: one document per signed-in `user` principal, `null`, meaning memory off, for unattended, service, schedule, and anonymous callers) and `brain.ts` (`factoryBrain({ writable: true })` from `agent/lib/memory/brain.ts`: scope is `FACTORY_REPO` lowercased, `maxCharacters` 8000). The analyst, implementer, and reviewer mount the same brain read-only at `agent/subagents/<id>/memory/brain.ts` (`factoryBrain({ writable: false })`); the brain's namespace is eve's `defaultNamespace` with a fixed node id, which is what makes the orchestrator and the stations resolve one store. There is no read tool: eve recalls each slot's document before every turn. The model writes through `<slot>__save_memory` and `<slot>__remove_memory` (`brain__save_memory`, `preferences__remove_memory`, and so on). Brain writes are gated by `trustedWrites()`: unattended runs get no brain tools at all, everyone else gets them behind `factoryBrainPolicy` (trusted callers write directly, others wait for approval). Storage is a private Vercel Blob store when deployed (`eve integration setup file-memory` provisions it) and process-local memory in `eve dev`. To add a slot: create `agent/memory/<slot>.ts` with `defineMemory({ description, provider, scope })`, derive the scope from the resolved principal or a server-side constant (never model input), wrap the provider with `trustedWrites` when the document is shared, add a `memory/<slot>.ts` mount in each station that should recall it, then update the expected slot lists in `tests/surface/discovery.test.ts` and the write-tool lists in `evals/helpers.ts`.
- **`git` and `gh` through `bash` are the GitHub surface.** There is no GitHub tool: agents run the real binaries in their own sandbox through `bash`, which is eve's built-in tool wrapped by `bashTool({ environment, role })` in `agent/lib/github/tools.ts` (`"orchestrator"` at `agent/tools/bash.ts`, `"reader"` on the analyst and reviewer, `"implementer"` on the implementer). `analyzeCommand` in `agent/lib/github/shell.ts` sorts each command into one of four kinds. On the orchestrator only the `gh` kind is accepted, and the runtime always runs it itself (see the orchestrator bullet below); the other kinds and the shell path are the stations'. `plain` names neither `gh` nor a networked `git` command (`fetch`, `pull`, `push`, `clone`, `ls-remote`) and runs in a station's shell with no credential; that check is loose and errs toward attaching a read-only credential (`git stash push` counts). `shell` names one in any shape and runs in a station's shell under a read-only lease, with the placeholder exported for the wrappers. `gh` (the whole command is `gh` commands with literal arguments, joined by `&&`, `;`, or new lines; a bare `gh`, `gh help`, `gh version`, `gh -h`, or a `gh` command with `--help` or `--version` is `shell` instead) runs the same way on a station when every step reads. On the orchestrator it is never run by a shell, reads included: the runtime runs the parsed steps itself by absolute path (`/usr/bin/gh`), each read under a `repo-read` lease and each write under a `repo-triage` lease, skipping a step joined with `&&` after a failure and still running a step after a later `;`, as a shell does. A step the runtime refuses only once it runs (a missing `--body-file`, an issue number that is a pull request) fails the command when nothing has run yet; after an earlier step has run, the result reports that step as failed and keeps the earlier output. `push` (the whole command is one `git push`, implementer only) is likewise run by the runtime, under a `repo-push` lease. The lexer is narrow on purpose: a command it does not fully understand is `shell`, never an error, and `shell` cannot write. `.github/ARCHITECTURE.md` (data flow, step 7) walks through one command end to end. Three layers keep this safe. (1) The argv allowlist: `parseGh` in `agent/lib/github/cli.ts` accepts only the commands and flags in its `COMMANDS` table and reduces each invocation to one effect (`read`, `label`, `comment`, `state`, `draft-pr`, `write`, `ship`, or `forbidden`); `--repo` must name `FACTORY_REPO` and is stripped because `GH_REPO` pins the repository; `gh api` is GET-only and limited to `repos/<FACTORY_REPO>/...`; there is no merge, no `pr review`, no `--web` or `--editor`. A single-valued flag may appear once, because `gh` honours the last occurrence (only the label, assignee, and reviewer flags and `--header` repeat, listed in `REPEATABLE_FLAGS`); callers pass text with `--body` or `--body-file <path>`, and `inlineBodyFiles` (`shell.ts`) turns the file form into `--body` before parsing, so the allowlist itself knows only `--body`; a `--search` value may not carry a `repo:`, `org:`, `user:`, or `owner:` qualifier, since those leave the repository; and selectors are validated (a numeric run id, a release tag, a workflow id or file name, `repo view` on the factory repository only). `parseGitPush` in `agent/lib/github/git-cli.ts` reads the words after `git push`: it accepts `origin` as the only remote word and the push goes to the literal repository URL (after `rewriteGuard`, see Security), takes one plain branch name (none, or `HEAD`, means the checked-out branch, which the tool reads and validates), pushes only to branches under `FACTORY_BRANCH_PREFIX` (default `factory/`), refuses `main`/`master` whatever the prefix is, and accepts no flag but `-u`/`--set-upstream`, so there are no force, delete, mirror, or tag pushes; fetch and pull run in a station's shell and accept any branch. `parseGitFetch` in the same file is for one case only, a deployment that cannot issue a read-only token (see Security), where the runtime runs a station's `git fetch` itself. (2) The policy: `agent/lib/github/approval.ts` is the single place an effect and a caller class become run / wait for approval / denied (`bashPolicy(role)` on every `bash`, through `shellDecision`; `stationPolicy` for the `run_<id>` tools). `plain` and `shell` run on a station, since they hold no credential that writes, and are denied on the orchestrator, which has no shell (`shellAvailable`), with the `GH_ONLY` message. A `gh` list of more than 12 commands (`MAX_GH_STEPS`) is denied. Each step of a list is parsed, and a step the allowlist refuses denies the command; a step that would wait for a person's approval and uses `--body-file` is denied too, with a reason that says to use `--body`, because the approver could not see the file's text; on the orchestrator each effect goes through `ghEffectDecision` and the strictest outcome decides, on a station only reads run. A push is denied unless the caller is the implementer and `parseGitPush` accepts it. One check needs GitHub and so lives in the tool: `issue close` and `issue reopen` look the number up first (`assertIsIssue` in `tools.ts`) and refuse a pull request, failing closed when the lookup gives no answer. (3) The credential lease in `agent/lib/github/lease.ts`: each command gets a random placeholder as its credential, the sandbox firewall swaps it for a freshly minted installation token only on requests carrying that placeholder, the policy resets to the sandbox's base egress policy in a `finally` (`endLease` tries up to `LEASE_RESET_ATTEMPTS`, 3, times, and a reset that still fails is an error), and leases are serialized per sandbox. `withShellLease` holds the lease for a shell command, is fixed at `repo-read`, and mints strictly, so `FACTORY_TOKEN_FALLBACK` never widens it; `runGh` and `runGitPush` lease the tokens that write, only to commands the runtime parsed itself. Tokens are scoped to the one repository and to a permission set per scope: `repo-read`, `repo-triage` (issues and pull requests write, contents read, so it cannot merge or push), and `repo-push` (contents write, the implementer's push only; `workflows:write` is added only when `FACTORY_ALLOW_WORKFLOW_CHANGES=1`).
- **What a GitHub command must look like.** The orchestrator has no shell, so every command it issues, reads included, must be the whole `bash` command: one `gh` command or several joined with `&&`, every argument literal, shaped with `--json` and `--jq`. A pipe, a redirect, a variable, a substitution, a glob, a comment, or a `NAME=value` prefix makes the command `shell`, which the orchestrator's `bash` denies. Long text goes through `--body "$(cat <<'EOF' ... EOF)"` (the delimiter must be quoted). The runner also takes `--body-file <path>`, but the orchestrator has no way to create a file and a station cannot write to GitHub, so nothing points an agent at it; a command that waits for a person's approval has to use `--body`. One command holds at most 12 `gh` commands. On a station, reads work anywhere in a command, pipes and scripts included (the exception is a deployment that cannot issue a read-only token, where a station has no `gh` at all and a fetch must be the whole command; see Security), and a `gh` command that would change something is refused: by the policy as a whole command, and by the `gh` wrapper or the read-only token inside a shell command. `git push origin <branch>` must be the whole command too (`cd repo && git push ...` and `git -C repo push ...` are also accepted), on the implementer only, to branches under `FACTORY_BRANCH_PREFIX` only. Four places tell agents this and must agree: the tool description (`GITHUB_NOTES` in `tools.ts`), the wrappers' hints (`shims.ts`), the denial reasons in `approval.ts` (`GH_ONLY` among them), and the agents' instructions.
- **The wrappers are a convenience and a guardrail, not the security boundary.** `agent/lib/github/shims.ts` builds two POSIX `sh` scripts that `installFactoryTooling` writes to `/usr/local/bin/gh` and `/usr/local/bin/git`, ahead of the real binaries on `PATH`. The `gh` wrapper attaches the lease's placeholder as `GH_TOKEN`, pins `GH_REPO` and refuses a `--repo` that names another repository, turns prompts off, keeps `gh` to the command paths in `GH_COMMANDS` (it finds the command path past a leading `-R` or `--repo`), and refuses a path in `GH_WRITE_COMMANDS` with a hint. The `git` wrapper passes everything straight to git except `fetch`, `pull`, `push`, `clone`, and `ls-remote`. With a lease in the environment it attaches the placeholder to those as an `http.extraheader` and prints a hint after a failed push; with no lease it is a plain `exec` of the real git for every subcommand and adds no output, so a repository's own tooling and tests see ordinary git. Keep it that way, and print wrapper messages with `printf '%s\n'`, not `echo`. On a station both are files in a sandbox where the agent has a shell and sudo, so anything a wrapper refuses, the real binary would still try. The boundary is the credential and the runtime's own parse and approval; never move a check that matters into a wrapper alone. Commands the runtime runs itself use `RUNNER_PATH` (`/usr/bin:/bin`), which skips the wrappers, so the orchestrator never reaches them.
- **The orchestrator has no shell, and no `write_file`, `edit_file`, or `agent`.** `agent/tools/bash.ts` is the wrapped `bash`, and `shellAvailable(role)` in `approval.ts` is false for the orchestrator whoever the caller is. Its `bash` accepts only whole `gh` commands (one, or several joined with `&&`), which the runtime parses against the allowlist, holds to the caller's trust class, and runs itself through `runGhSteps`, reads included; any other command (a pipe, `ls`, `git status`, a script, `gh --help`) is denied with the `GH_ONLY` message. `bashPolicy` and the tool's `execute` both make the check, so keep both. `agent/tools/{write_file,edit_file,agent}.ts` export `disableTool()`, because the orchestrator routes work and does not write code, and the built-in `agent` tool would let it bypass the stations. Don't re-enable those three. For `write_file` and `edit_file` that is a security rule: never re-enable them on the orchestrator, and never give it any other way to start a process or write a file in its sandbox. That sandbox is where the runtime runs the orchestrator's approved writes, and its being free of anything the orchestrator put there is what makes the allowlist and the per-caller policy the limit. Stations always have a shell.
- **A shell command never holds a credential that can write.** Only the stations have a shell. Keep it that way there: never lease `repo-triage` or `repo-push` to anything a shell runs (`withShellLease` takes no scope for that reason). Local git (status, diff, checkout, commit) needs no credential on a station, and a fetch runs under the read-only lease. And never hand the GitHub channel's `turn.started` back to its default, whose checkout leaves the installation token attached to every git request from the root sandbox and never takes it off (`agent/channels/github.ts` replaces it with `checkoutForTurn` from `agent/lib/github/checkout.ts`, under a read-only lease). The orchestrator has no shell to use that token with, but the factory does not rest on that alone: no token is left standing on any sandbox.
- **Extending the `gh` allowlist:** add the command to `COMMANDS` in `agent/lib/github/cli.ts` with every flag it may take (value flags and boolean flags are listed separately, anything unlisted is refused) and an `effect` function that returns the narrowest effect that is true; add a command that changes GitHub to `GH_WRITE_COMMANDS` as well (the `gh` wrapper reads that list, and `tests/github/gh-cli.test.ts` holds it against the effects the parser reports); a `--body` flag needs no extra registration, since the parser records each body's position for the runner (`GhInvocation.bodies`); add a flag to `REPEATABLE_FLAGS` only when `gh` adds its values together; then add a row to `MATRIX` in `tests/github/approval.test.ts` stating the outcome for every caller class (and to `READ_ROWS` there when the command only reads), the command's flags to the literal `FLAGS` table and its effect to the per-command effects in `tests/github/gh-cli.test.ts`, and parse cases in that file (`tests/github/gh-contract.test.ts` then checks the new command, its flag spellings, and whether each flag takes a value against the installed `gh`). A new effect kind needs a case in `ghEffectDecision` (the `satisfies never` default forces it) and a row in the `EFFECTS` table in `tests/github/approval.test.ts`. Non-read commands run on the `repo-triage` token, so a command that needs another permission also needs a deliberate `TOKEN_SCOPES` change in `lease.ts`. Adding or removing a command changes the `gh` wrapper, which embeds both lists, and that re-keys the sandbox templates by itself (below). `--body-file` is accepted from callers through `inlineBodyFiles`, which turns it into `--body` before parsing; the allowlist itself still knows only `--body`, so don't list `--body-file` on a command. Never widen `gh api` beyond GET, never accept field flags, interactive flags, or `--`, and never add merge or `pr review`.
- **Approval-gated tools must not live inside a station.** A declared subagent can request input, but nothing is watching a station's own card, so a station tool that returned `user-approval` would strand the run. Anything needing approval belongs on the root (the orchestrator's `bash`, `triage_work_item` when it applies labels, the brain's write tools); station tools only ever return run or denied (`bashPolicy` with the `reader` or `implementer` role), and the implementer's push is bounded in code (the factory's own prefixed branches only, validated names, leased credential).
- **`agent/lib/trust.ts` is the single trust authority.** Channels stamp trust at dispatch; the policies in `agent/lib/github/approval.ts` read the stamps and return `not-applicable` / `user-approval` / `denied`. There are three caller classes: unattended (the constructed autonomous principal, from `stampAutonomous` for label intake and CI fixes or `autonomousForTicket` for the intake API), trusted (`stampTrusted`, or a schedule turn), and everyone else (the dev TUI, an unstamped session). A summary-only run (`stampSummary`, read back with `isSummaryOnly`) is the unattended class narrowed further: `onPullRequest` stamps it for a pull request opened by anyone, and it may read and comment on that one pull request and nothing else; labels, close and reopen, draft PRs, every other write, and every station are denied. The class decides what a caller's `gh` commands may do; it does not decide whether there is a shell, which the orchestrator never has (`shellAvailable` in `approval.ts`). A new capability never invents its own caller check; gate on the existing predicates.
- **Sandboxes** share their create options and init logic via `agent/lib/github/repo-sandbox.ts`. Every environment (root included) passes `FACTORY_SANDBOX_CREATE_OPTIONS`: one kept snapshot and a 14-day expiration, so template snapshots survive quiet stretches without accumulating, plus a `prepare` step that runs once per template snapshot. `prepare` is `installFactoryTooling` from `agent/lib/github/tooling.ts`: it installs `gh` from the image's Ubuntu archive (`/usr/bin/gh`) and pnpm (`npm install -g pnpm`, since eve's base image does not ship it), writes the `gh` and `git` wrappers to `/usr/local/bin`, and fails the build if a binary is missing or either name does not resolve to its wrapper. A template is keyed by its own sandbox file and create options, not by imported modules, so `FACTORY_TOOLING_VERSION` rides along in the create options' `env`. It is a digest of the whole install script, wrappers included, so a change to the installer, a wrapper, or the command lists a wrapper embeds re-keys every template; nobody bumps it by hand. Each station's `defineSandbox(...)` opens the environment from `createFactoryEnvironment`, then `factoryInit` clones the factory repository into `/workspace/repo` under a read-only credential lease, ends the lease, and runs `FACTORY_SETUP_COMMAND` with no GitHub credential (whatever it runs gets the sandbox's base egress policy and nothing else), once per session. `cloneCommand` also widens the shallow clone's fetch refspec, which is what lets a station check out a branch it fetched with a plain `git checkout`. The git commands the factory writes itself (the clone, the orchestrator's per-turn checkout, the push) target the literal remote URL, so the URL a checkout has configured for `origin` cannot redirect them, with the token attached at the sandbox firewall. A `url.*` rewrite rule in git's config still could, so the ones that run after an agent has had the sandbox (the push, the fallback fetch, the per-turn checkout) start with `rewriteGuard` (see Security). The clone and the per-turn checkout have a ten-minute limit (`LEASED_GIT_TIMEOUT_MS`). A fetch an agent runs in its shell does use the checkout's `origin`, under a credential that only reads.
- **Sandbox egress is an allowlist by default.** Every `sandbox.ts` (root included) opens with `environment.open(factoryOpenOptions())`, whose network policy is `basePolicy()` from `agent/lib/github/egress.ts`: GitHub's hosts and the public package registries, each named in full, no wildcards. A credential lease is laid over that policy (`withBasePolicy`) and ends by putting it back, so nothing in the factory sets `allow-all` by hand; `tests/github/egress.test.ts` holds both. `FACTORY_SANDBOX_ALLOWED_DOMAINS` adds hostnames (validated, and a bad entry fails the sandbox open, it is not dropped), and `FACTORY_SANDBOX_EGRESS=open` restores open egress, where a lease is byte-for-byte what it was before (`"*": []` plus its rules, then `allow-all`). The rest of the test suite runs in open mode for that reason (`vitest.config.ts` says why); a new sandbox or a new policy call goes through `basePolicy`, never a literal. Adding a host to the defaults is a decision about where repository contents can go: add one only for a registry or a GitHub endpoint, and keep it an exact hostname. The policy is passed to `open()`, not to the environment, so the template build still reaches the image's package archive.
- **Install scripts are off in station sandboxes.** `factoryInit` writes the user-level "do not run install scripts" setting for npm, pnpm (both config locations, since pnpm is unpinned), and both Yarn generations (`agent/lib/github/install-scripts.ts`) before `FACTORY_SETUP_COMMAND` runs, in the same command as the git identity so a session's init stays one step. The command only appends a line a file does not hold yet, so it is safe when eve runs init again. It covers dependencies' install scripts and the repository's own; scripts run by name (`pnpm run build`) are untouched, which `tests/github/install-scripts.test.ts` checks against the real package managers. `FACTORY_ALLOW_INSTALL_SCRIPTS=1` turns it off. It is a default, not a boundary: the files sit in a sandbox the agent can write.
- **Tools** run in the app runtime (full `process.env`), one default export per file. A tool that runs a command in a sandbox gets it with `ctx.getSandbox(environment)`, importing the mounting agent's own `environment` export from its `sandbox.ts` (that typed handle is what exposes `setNetworkPolicy` to the lease). Gate a tool whose outcome depends on the caller with a policy from `agent/lib/github/approval.ts` (here: `bashPolicy` on `bash`, `labelDecision` on `triage_work_item`, `stationPolicy` on each `run_<id>`); a tool that only reads needs no approval (`diagnose_ci_failure`).
- **Connections** are MCP servers: `linear` (`https://mcp.linear.app/mcp`, app-scoped auth shared through `linearAuth` in `agent/lib/constants.ts`). Its connection-wide `approval` predicate denies writes on unattended runs.
- **Skills** are load-on-demand. A packaged skill (`<name>/SKILL.md`) requires `description` frontmatter; that description is the routing hint. The skills here are `writing-quality`, `triaging-issues`, and `github-linear-bridging`. Skills are per-agent: stations don't see the root's skills.
- **Tests** live in `tests/` (`pnpm test`, vitest, config in `vitest.config.ts`). The suite is deterministic and offline: no model, GitHub, Linear, Blob, or sandbox, every boundary replaced with an in-process fake. It covers the `gh` allowlist and the push parser, the command sorter and its lexer (`shell.test.ts`), the `gh` and `git` wrapper scripts (`shims.test.ts`), the install script and its digest (`tooling.test.ts`), the authorization matrix, credential leases and token scopes, the `bash` tool, with an adversarial command corpus replayed per role (`tools.test.ts`), the orchestrator's per-turn checkout (`checkout.test.ts`), the GitHub dispatch hooks (all in `tests/github/`), the trust stamps, model map, bot name, and bootstrap diagnostics (`tests/lib/`), the brain slot and `userScope` on eve's real file memory with its in-memory backend (`tests/memory/`), decision-model triage and its `gh` helpers (`tests/triage/`), the intake contract and route handlers (`tests/intake/`), the station schemas and `stationOutput` (`tests/stations/`), type-level contracts (`tests/types/*.test-d.ts`, checked by vitest's typecheck mode), and the assembled surface read from `eve info --json` (`tests/surface/`: tools per agent, memory slots, routes). Some files use local binaries and no network: `tests/github/git-real.test.ts` and `tests/github/checkout.test.ts` run the rendered git commands against a temporary bare repository, `tests/github/shell.test.ts` compares the lexer with real `sh` and `bash`, and `tests/github/gh-contract.test.ts` checks every allowlisted command and flag, and whether each flag takes a value, against the installed `gh`'s own help. The git and `gh` cases are skipped where the binary isn't installed, unless `FACTORY_REQUIRE_CLI_TESTS=1` is set (CI sets it), which turns a missing binary into a failure. Anything that can be decided without a model belongs here: a parser rule, a policy outcome, a schema bound, a dispatch decision, a tool that must or must not exist. Shared caller fixtures are in `tests/helpers.ts`.
- **Evals** live in `evals/` (`defineEval`, one file per case; `evals.config.ts` holds run-wide config; `t.judge` uses eve's default decision model, `typesafe-ai/jev`). They need model credentials and cover what only a model run can show; `pnpm validate` only lints and type-checks them. Category directories are the failure taxonomy (`routing/`, `safety/`, `pipeline/`). Every GitHub operation is a `bash` call, so `helpers.ts` classifies a call by its command with the project's own `analyzeCommand` and `parseGh`: read-only evals assert `noGithubWrites` (deny-by-default: a `gh` list with any step that is not an allowlisted read, including a step the allowlist refuses, counts as a write, and so does a `git push`; `plain` and `shell` commands do not, since the orchestrator's `bash` denies them) and `notCalledTool` over the memory write tools. Tags: `fast` (cheap loop), `slow`, `needs-connect` (asserts calls that must succeed against real Connect auth), `pipeline` (pushes a real branch; opt-in).
- After editing, **check LSP diagnostics / `pnpm typecheck`** and fix type errors before moving on.

## Code style

- Linting and formatting are handled by **Ultracite** (a Biome preset). Run `pnpm check` before finishing and `pnpm fix` to auto-fix. Config is in `biome.jsonc`; the kebab-case filename rule is disabled there because eve tools use snake_case names, and a `tests/**` override relaxes three rules that only guard runtime cost.
- TypeScript strict; ESM. Relative imports under `agent/`, `evals/`, and `tests/` carry a `.js` extension; `scripts/` imports with `.ts` because Node runs those files directly. The `#lib/...` alias (the `imports` map in `package.json`) points at `agent/lib/`. Prefer `const`, arrow functions, optional chaining / nullish coalescing.
- Validate tool input/output with `zod` schemas.
- Prose in markdown files is not hard-wrapped: write each paragraph or bullet as one line.
- Agent-facing text (instructions, skill bodies, tool and subagent descriptions) follows the "How you write" rules in `agent/instructions.ts`: no em dashes, no machine-made words, no bold for emphasis. It carries behavior only, never framework plumbing (how approvals render, sign-in flows) or references to tools and skills the reading agent can't access. That matters most for station instructions, since stations see none of the root's surface.

## Security

- **Never ask the user for API keys, client secrets, or any other credentials.**
- **Never commit secrets.** `.env*` is gitignored. Connector UIDs are read from env (`GITHUB_CONNECTOR`, `LINEAR_CONNECTOR`); GitHub and Linear auth is brokered by Vercel Connect (tokens resolved per call, never exposed to the model) and Blob auth is via the project's OIDC token. `FACTORY_REPO` is required at module load (`requireEnv`), so a missing value fails discovery; `FACTORY_SETUP_COMMAND` is optional, as are `FACTORY_INTAKE_TOKEN`, `FACTORY_INTAKE_CALLBACK_HOSTS`, `FACTORY_INTAKE_CALLBACK_SECRET`, `FACTORY_TOKEN_FALLBACK`, `FACTORY_ALLOW_WORKFLOW_CHANGES`, `FACTORY_SANDBOX_EGRESS`, `FACTORY_SANDBOX_ALLOWED_DOMAINS`, `FACTORY_ALLOW_INSTALL_SCRIPTS`, and `FACTORY_SIGNED_COMMITS`.
- **GitHub safety is structural; keep it that way.** The command sorter (`shell.ts`) decides which credential a command can get, and a shell command never gets one that can write. `shellAvailable` (`approval.ts`) decides whether an agent has a shell at all, and the orchestrator does not. The argv allowlist and the push parser (`cli.ts`, `git-cli.ts`) decide what can run with a credential that writes, `approval.ts` decides who may run it, and `lease.ts` bounds what the credential can do if the rest is wrong. The wrappers in the sandbox are none of these layers: they are a convenience and a guardrail. The push targets the literal `https://github.com/<FACTORY_REPO>.git` URL, never `origin` (remote config in a sandbox is model-writable; the next bullet covers URL rewrite rules), and pushed branches pass `validateBranch`, which requires the `FACTORY_BRANCH_PREFIX` prefix (default `factory/`) and refuses `main`/`master` by name regardless. That rule is a second layer, not a replacement for branch protection on the default branch, which is still required: the check lives in the push parser, not in the token. A git command the runtime runs itself (the push, the clone, the per-turn checkout) runs with hooks disabled and HTTPS as the only allowed protocol. Callers pass `gh` bodies with `--body` or `--body-file <path>`; for a command it runs, the runtime reads the named file itself with a bounded read (`readBodyFile` in `tools.ts`: `/usr/bin/head -c`, one byte past the body limit), then writes every body to a file of its own and passes `--body-file` (`bodiesToFiles`, working from the positions the parser recorded), so model-written prose never sits on the command line the runtime runs. A command that would wait for a person's approval may not use `--body-file` (`ghStepDecision` denies it with a reason that says to use `--body`), because the file is read after the approval and the approver could not see its text. A file's text is also whatever is in the checkout, which a contributor's pull request controls, and it is read after the policy has judged the command. Two things keep it from changing the command. The parser removes `-R/--repo` only where a flag can be (`stripRepoFlagFromRest` in `cli.ts` steps over each flag's value), so text that reads `--repo=...` stays the body and cannot make `--body` take the next word, such as `--draft`, as its value. And `resolveStep` in `tools.ts` parses the step twice, as approved and with the text in, and runs it only when the two are the same command and effect, word for word apart from the body (`isApprovedCommand`). Keep the second check even though the first makes it unreachable today: it is what holds if the parser is ever wrong again. Never hand the GitHub channel's `turn.started` back to its default, whose checkout leaves the app's installation token attached to every git request from the orchestrator's sandbox. Don't weaken any of these when adding a capability.
- **A literal URL does not stop a git URL rewrite rule.** Naming the URL keeps the URL a checkout has configured for its remote from redirecting a command the runtime runs. A `url.<base>.insteadOf` or `pushInsteadOf` rule still could, since git applies it to a literal URL too and git's config files in a station's sandbox are the agent's to write. So the push, the fallback fetch, and the per-turn checkout start with `rewriteGuard` (`git-cli.ts`), which refuses to run when the repository's config file, its per-worktree config file, the user's, or the system's (includes followed) holds a `url.*` setting; configuration passed through the environment is the runtime's own and is not looked at. The guard reads the files immediately before the command, so if a rule gets past it, the bound is the token: the firewall attaches it only on GitHub's hosts, and it covers the factory repository alone unless `FACTORY_TOKEN_FALLBACK=installation` widened it. Put the guard at the front of any new git command the runtime runs under a lease in a sandbox an agent has used.
- **The implementer's push runs in the same sandbox as the implementer's shell.** While the push runs, its placeholder can be read by anything else the run left in that sandbox, and a run could have replaced `/usr/bin/git` or a shell start-up file beforehand. So an implementer run taken over by its input can push to any branch the `repo-push` token allows on the factory repository, despite the branch-prefix rule. What bounds it is the token's scope (contents on the factory repository, or whatever a widened token holds under `FACTORY_TOKEN_FALLBACK`) and branch protection on the default branch, which stays required. `.github/ARCHITECTURE.md` (Residual risks) has the full account.
- **A signed push is the same push with more requests.** With `FACTORY_SIGNED_COMMITS=1`, `runGitPush` writes `PUSH_SIGNED_SCRIPT` (`agent/lib/github/push-signed.ts`) into the sandbox for that one command and runs it in place of `git push`: it recreates the branch's new commits through GitHub's Git Data API, which is what makes GitHub sign them, moves the ref, and moves the local branch onto the signed commits (same trees, new SHAs). Everything that bounds a plain push still holds and must keep holding: the branch comes from `validateBranch`, the repository and the fetch URL are the runtime's literals handed over in the environment (the script reads nothing about the remote from git config), the ref update is never forced, the scope is `repo-push`, hooks are off, and `rewriteGuard` runs first. Two things differ: the lease covers the API hosts as well as the git hosts (`LeaseKind` `shell`) for the whole replay, and `PATH` is left to the sandbox so `node` resolves, with git's `PATH` passed to the script, which runs git by absolute path. The script asks GitHub whether a commit exists before recreating it, because the checkout's remote-tracking refs are model-writable and a stale one must not turn the base branch's history into copies. Keep the script free of backticks and `${` (it is a string), and test changes to it in `tests/github/push-signed.test.ts`, which runs it with the real git against a stand-in for the API.
- **The GitHub channel uses a narrowed token too.** `agent/channels/github.ts` overrides the connector's `installationToken` with `mintChannelToken` (`lease.ts`): the `repo-triage` scope on the factory repository, which covers what the channel does (read the thread, reply, react, check a labeler's permission). Unlike a leased scope it falls back to the connector's own token when narrowing is refused, whatever `FACTORY_TOKEN_FALLBACK` says, and logs it: the channel is how the factory answers at all, the token stays in the app runtime, and the fallback is what the channel used before. Keep the override in the channel file; `credentials.ts` has to stay the raw connector, since the lease ladder's last rung reads it.
- **On the orchestrator the allowlist and the per-caller policy are the limit.** The orchestrator can start no process and write no file in the sandbox where its writes run: `bash` gives it only whole `gh` commands, which the runtime runs, and `write_file` and `edit_file` are disabled.
- **The token never enters a sandbox.** A leased process only ever holds a placeholder; the real installation token exists in the app runtime and at the sandbox firewall. Output is redacted for the exact leased token (not by pattern). Output of a command the runtime runs itself is also truncated before it reaches the model; `run view` output keeps its tail, where a log's failure is, and every other command keeps its head. Token narrowing fails closed by default: a scope gets its required and optional permissions, then the required ones alone, and if neither is granted the command fails with a message naming the permissions to check. `FACTORY_TOKEN_FALLBACK` (unset or `none` by default) lets a deployer add wider rungs: `repository` adds every permission the app holds, still on the factory repository; `installation` adds that and then the connector's plain installation token (every permission, every repository the installation covers). Each use of a wider rung logs a console warning. A wider rung never reaches a shell command: `withShellLease` mints with `strict`, so a shell command holds a token within `repo-read` or none at all (`NarrowTokenError`). Strict minting walks only the scope's own rungs, never reads or writes the memo the runtime's own commands use, and keeps its own short memory of a refusal instead (`STRICT_REFUSAL_TTL_MS`, 60 seconds). When no read-only token can be issued, `runWithoutShell` in `tools.ts` has the runtime run a station's command that is nothing but one `git fetch` (`parseGitFetch`, `runGitFetch`), under a lease that does follow the setting; anything else that names `gh` or a networked `git` command (any `gh` command at all, a pipe, a script, `git pull`) is refused with the `WHOLE_COMMANDS_ONLY` message. A station's sandbox is the agent's, so a wider token is never put behind `gh` there: `gh`'s reads and writes are the same kind of request to the firewall, and anything else running in the sandbox could read the placeholder and write with it. For the fetch, and for any read lease that took a wider token (the clone, the per-turn checkout), `withLease` adds a path rule to the firewall (`FETCH_PATH` in `lease.ts`), so the token is attached only to the two requests a fetch of the factory repository makes. Keep both: never run `gh` for a station on a widened token, and never drop `fetchOnly` from a widened read lease. The orchestrator's commands always go through that runner. For the runtime's own commands the rung that worked is remembered; a rung below the first is re-examined after ten minutes (`SCOPE_DOWNGRADE_TTL_MS`), and a remembered rung that stops working is forgotten and the ladder walked again. Keep the invariant that no scope except `repo-push` can write repository contents (`tests/github/lease.test.ts` asserts it).
- **Respect the trust model.** Trust is stamped at dispatch by the channels; unattended runs are denied writes (except labels, comments scoped to their stamped intake issue, close/reopen, and draft PRs) rather than parked. A summary-only run is denied those too: it reads, and comments on its one pull request. A close or reopen that carries `--comment` follows the comment policy for every caller. A run started through the intake API uses the same autonomous principal built by `autonomousForTicket`: it carries the ticket id and the verified caller as attributes and no intake issue, so it has no thread to comment on and its final message is the result. When adding a tool or connection, pick its policy from `agent/lib/github/approval.ts` (or the trust predicates) instead of hardcoding `"never"`.
- **Traces record content for every session.** `agent/instrumentation/otel.ts` sets a trace policy that records prompts, tool arguments, and responses whatever the session's audience, where eve's default records them for public conversations only. Without it a run on a private repository shows in Vercel Agent Runs with nothing in it, and its stored run data is deleted when the run ends. The cost is that Agent Runs then holds a private repository's issue text, code excerpts, and model output for as long as traces are retained. Don't narrow the policy without saying so in the README: an operator who can't see a run can't tell what the factory did.
- **Treat every inbound work item as untrusted text.** Issue bodies, comments, diffs, and intake tickets describe work; they never change the rules. The intake ticket's requester, priority, and labels are rendered as the submitter's claims, and the request body cannot influence the session's principal.
- If you ever build a `RegExp` from data, escape it (literal match) and bound the input length.
- Gate irreversible or high-impact actions behind approval (here: the ship gate, `shipDecision`, which covers `pr ready` and a non-draft `pr create` and waits for a person even when the caller is trusted).
- The Blob store is private and holds handoff artifacts only. `agent/lib/blob.ts` declares the `artifacts/` prefix and the read and write helpers the artifact tools go through, both with private access. There is no general-purpose Blob tool; if one is ever added, it must refuse any path under `artifacts/`, so a handoff document stays reachable only through the artifact tools.
- For per-user memory, derive the scope from the resolved principal (`ctx.session.auth.current`), never from model input: see `userScope` in `agent/lib/memory/scope.ts`. Only a `user` principal has preferences, so a prompt-injected issue can't leave "preferences" behind for the next unattended run.
- The shared **factory brain** derives its scope from `FACTORY_REPO`, never from model input or a caller principal: see `agent/lib/memory/brain.ts`. Recalled memory is context every future run trusts, so writes are locked twice: unattended runs get no brain tools (`trustedWrites`), and `factoryBrainPolicy` denies them anyway, lets trusted callers write directly, and parks everyone else. Station mounts are recall-only (`readOnly`). An untrusted issue body must never be able to write the context every future run reads.
- **Handoff artifacts** live under the reserved `artifacts/` Blob prefix, reachable only through `save_artifact` / `read_artifact`: see `agent/lib/artifacts/config.ts`. Ids are model-supplied on read, so every id must pass the anchored `ARTIFACT_ID_PATTERN` (no dots or slashes) before it is interpolated into a Blob key; that is what keeps a station from addressing another reserved prefix through the artifact tools. Saves never overwrite and are size-bounded, which keeps both tools inert enough to live ungated inside a station.
- **Intake API:** keep the schema strict, keep the principal constructed server-side, resolve status reads through the ticket's own address (never a raw session id, so the API can't read a session GitHub or Linear started; the address includes the caller, so one caller can't read another's ticket), return only `publicError`'s `{ code, id }` for a failed run, and keep callbacks behind the host allowlist and the signature. A callback URL the server will POST to is a request-forgery vector.

## Before committing

- `pnpm validate` passes (Ultracite check, `tsc`, `vitest run`, and the discovery check with 0 errors / 0 warnings).
- A change to the `gh` allowlist, the command sorter, a wrapper, a policy, a lease, a dispatch hook, a memory slot, or the intake contract comes with a test under `tests/`.
- No secrets, `node_modules`, or build output (`.eve`, `.vercel`, `.output`) staged.
